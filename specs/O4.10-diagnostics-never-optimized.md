# O4.10 Diagnostics are never optimized

## Requirement

> **Diagnostics** (reported, never optimized): `tool_track_max_mm`, `joint_track_rms_deg` (worst joint),
> `tool_lag_ms`, `stop_error_mm` (median), `saturation_share_pct`, `energy_j` (positive mechanical work, labelled
> "motor energy"), `tool_jerk_rms_m_s3`, `host_compute_ms_p95` (the solution's own `tick` time), `wall_time_s`.

From [OBJECTIVES.md §4 The score](../OBJECTIVES.md#4-the-score), ruler v1. OBJECTIVES.md is the frozen ruler and the one source of every number; this note explains it and never overrides it.

## What it means

Every scorecard carries these numbers. They explain a score (where the error is, how much lag, how hard the motors
work, how long `tick` takes); they never rank one. An agent reads them to decide what to try next, but a solution that
only improves a diagnostic has not improved.

## Why

OBJECTIVES.md says only "reported, never optimized". A reading, not the ruler's: one objective keeps the search honest,
and every extra number it optimized would be another one to game (Goodhart's law); the gates hold the limits that
matter.

## How it is checked

**No test**, and none required: it is a *should* about what the agent optimizes, not about code. What the code does
check is the ranking, which reads only admissibility, gate pass rate and the objective
([O4.9](O4.9-ranking.md)), never a diagnostic.
