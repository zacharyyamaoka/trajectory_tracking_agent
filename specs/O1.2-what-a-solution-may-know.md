# O1.2 What a solution may know

## Requirement

> **What a solution may know (clarified 2026-11-24, before any agent-written solution; no score changes):** it learns
> about the robot only through the boundary, exactly as on a real arm: the deployment's public fields (joint names,
> rates, bus, caps, limits, tool FK), the robot models robot_controllers *gives* the arm with the deployment's model
> error (`base_scenario(arm).model_error`, 10 % on every link), and its own experiments run through the boundary
> (commands in, joint states out: dev runs, or a calibration run such as robot_controllers' bus calibration). It never
> reads the plant's parameters (`UR5E_TRUTH`, the plant's MjModel, its masses, friction or armature), never calls
> `deployment.plant()`, and never uses a model with less error than it was given.
>
> A solution never edits this file, [`datasets/`](../datasets/) or [`src/trajectory_tracking_agent/ruler/`](../src/trajectory_tracking_agent/ruler/).

From [OBJECTIVES.md §1 The black box](../OBJECTIVES.md#1-the-black-box), ruler v1. OBJECTIVES.md is the frozen ruler and the one source of every number; this note explains it and never overrides it.

## What it means

A solution plays by a real arm's rules. It may read what any integrator could read off the arm's datasheet and wiring
(the deployment's public fields), start from the robot models it is given, which carry 10 % error on every link, and
learn the rest from its own runs through the boundary. It may not read the simulator's truth: the plant's parameters,
its MuJoCo model or the plant object itself. Nor may it peek at the scorer (the ruler) or the holdout tapes (CONTRACT
§2), or edit the ruler, the dataset or OBJECTIVES.md.

The generation-1 solutions identify friction and gravity from their own dev runs. That is allowed, because those data
came through the boundary; [ideas.md](../ideas.md) asks for a separate calibration run so identification stops being
fitted on the tasks it is scored on.

## Why

> WHY: a gain that comes from knowing the simulator's truth can't transfer to a real arm
> ([simulator exploitation](https://en.wikipedia.org/wiki/Reward_hacking));
> [`tests/test_solutions_honest.py`](../tests/test_solutions_honest.py) checks every solution's source for it.

(OBJECTIVES.md §1.) The search is only worth running if what it finds works on a robot whose truth nobody knows.

## How it is checked

- [`tests/test_solutions_honest.py`](../tests/test_solutions_honest.py) reads every `.py` in every solution folder (helper scripts too, since gen-1 solutions
  identify their models with scripts beside `solution.py`) and fails on each direct route to the truth: `UR5E_TRUTH`, the
  plant object, the plant's MuJoCo model, a model error of zero, the ruler, the holdout split.
- `test_a_solution_importing_the_ruler_is_refused`: a solution that imports the ruler fails closed and `evaluate`
  refuses it.
- `test_check_source_names_dataset_reads_but_not_docstrings`: a path into [`datasets/`](../datasets/) is flagged; a docstring that
  merely says "holdout" is not.

A source check, not a proof, as the honesty test says of itself: it catches the direct routes. The dispatcher also
reads each agent-written solution's diff.
